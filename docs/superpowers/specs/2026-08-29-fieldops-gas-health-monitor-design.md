# FieldOps GAS死活監視 設計仕様

**作成日:** 2026-08-29

**状態:** ユーザー承認済みPRDを設計仕様へ反映

**対象:** `https://fieldops-portfolio.onrender.com` の外形監視

## 1. 背景と目的

FieldOps PortalはRender Freeで公開しているため、無通信状態が続くとサービスが停止し、次のアクセスでコールドスタートが発生する。また、サービスまたはデータベースに異常が発生しても、管理者が公開画面を開くまで気づけない。

本変更ではGoogle Apps Script（GAS）を1時間ごとに実行し、公開済みのヘルスチェックを外部から確認する。結果はGoogleスプレッドシートへ記録し、異常発生時と復旧時だけメールで通知する。

この監視は可用性の観測だけを目的とする。15分未満のアクセスによるRender Freeのスリープ回避は行わない。

## 2. 成功条件

次の条件をすべて満たした時点で完了とする。

1. GASから`/health/live`と`/health/ready`を確認できる。
2. 監視結果が日本時間付きでGoogleスプレッドシートへ1実行1行で記録される。
3. 正常から異常へ変化したときだけ異常メールが1通送信される。
4. 異常が継続しても毎時間同じメールを送らない。
5. 異常から正常へ戻ったときだけ復旧メールが1通送信される。
6. Renderのコールドスタート中の画面を正常なヘルス応答と誤判定しない。
7. `runHealthCheck`の1時間トリガーが1件だけ登録される。
8. 正常、異常、復旧の3経路を実環境で確認できる。
9. GASソース、設定方法、停止方法がGitHubリポジトリに保存される。
10. 監視を停止してもFieldOps本体とRender設定に変更が残らない。

## 3. 対象範囲

### 3.1 含むもの

- Googleスプレッドシートに紐づくGASプロジェクト
- 1時間ごとの時間主導型トリガー
- `/health/live`と`/health/ready`のHTTP GET
- コールドスタートを考慮した再試行
- 監視履歴のスプレッドシート記録
- 状態変化時のメール通知
- 初期設定、手動確認、停止、再開の操作
- リポジトリ内の再現可能なGASソースと運用手順

### 3.2 対象外

- 15分未満の定期アクセス
- Render Freeのスリープ回避
- Renderの有料プラン変更
- 自動再デプロイ、自動再起動、データ初期化
- 公開デモに対する負荷試験
- FieldOps本体の画面、API、DBスキーマ変更
- 正常時の定期メール、日報、週報

## 4. 構成

Googleスプレッドシートを監視の操作画面兼履歴保管場所とする。紐づくGASが設定、実行、通知を担当する。

```text
1時間トリガー
  ↓
runHealthCheck
  ├─ GET /health/live
  ├─ GET /health/ready
  ├─ 結果を監視履歴シートへ追記
  ├─ 前回状態をScript Propertiesと比較
  └─ 異常または復旧時だけMailAppで通知
```

FieldOps本体には監視専用エンドポイントを追加しない。既存の匿名アクセス可能なヘルスチェックをそのまま使用する。

## 5. スプレッドシート設計

スプレッドシート名は`FieldOps 公開監視`とする。

### 5.1 `監視設定`シート

| 項目 | 初期値 | 説明 |
| --- | --- | --- |
| 公開URL | `https://fieldops-portfolio.onrender.com` | 末尾の`/`は保存時に除去する |
| 通知先メール | GAS実行ユーザーのメール | 空の場合は監視開始を拒否する |
| 実行間隔 | 1時間 | 固定。15分未満は提供しない |
| 再試行回数 | 5回 | 初回を含む |
| 再試行間隔 | 15秒 | コールドスタート待機用 |
| 監視状態 | 停止中／監視中 | 現在のトリガー状態を表示する |

利用者が編集する項目は公開URLと通知先メールだけとする。その他はコード側の安全な固定値として表示する。

### 5.2 `監視履歴`シート

次の列を左から順に持つ。

1. 実行日時（JST）
2. 総合結果（正常／異常）
3. live結果
4. live HTTP状態
5. ready結果
6. ready HTTP状態
7. 所要時間（秒）
8. 試行回数
9. エラー概要

履歴は追記専用とし、GASから既存行を更新・削除しない。

## 6. ヘルス判定

### 6.1 正常条件

各エンドポイントについて、次をすべて満たす場合だけ正常とする。

- HTTP状態が200
- 応答本文を前後空白除去後に比較し、`Healthy`である
- HTMLのRender起動画面ではない

`live`と`ready`の両方が正常なときだけ総合結果を正常とする。

### 6.2 再試行

初回が正常でなければ15秒待ち、最大5回まで同じ2エンドポイントを確認する。途中で両方が正常になれば成功として終了する。

GASの1実行上限を超えないよう、最大待機時間は約60秒、全処理は6分未満に収める。

### 6.3 異常条件

最大試行後も次のいずれかが残る場合は異常とする。

- ネットワーク例外またはタイムアウト
- 200以外のHTTP状態
- 応答本文が`Healthy`ではない
- `live`または`ready`の一方だけが失敗

エラー概要には資格情報、Cookie、レスポンスヘッダーを保存しない。本文は判定にだけ使用し、履歴やメールへそのまま転載しない。

## 7. 状態管理と通知

前回の総合状態はScript Propertiesの`LAST_STATUS`へ`UP`または`DOWN`として保存する。初回の正常実行は基準状態を保存するだけで、メールを送らない。初回から異常の場合は異常メールを送る。

### 7.1 異常メール

- 件名: `[FieldOps監視] 公開環境の異常を検知しました`
- 本文: 検知日時、公開URL、失敗したヘルスチェック、HTTP状態、試行回数、スプレッドシートへの案内

### 7.2 復旧メール

- 件名: `[FieldOps監視] 公開環境が復旧しました`
- 本文: 復旧日時、公開URL、直前の異常検知日時、スプレッドシートへの案内

通知先は`監視設定`シートのメールアドレスとする。メール送信失敗は監視結果と分離して履歴へ記録し、ヘルス判定自体を書き換えない。

## 8. 利用者操作

スプレッドシートを開いたとき、`FieldOps監視`メニューを追加する。

- `初期設定を作成`: 設定・履歴シートと見出しを作成する
- `今すぐ確認`: その場で監視を1回実行する
- `1時間ごとの監視を開始`: 既存の同一トリガーを整理して1件だけ作成する
- `監視を停止`: `runHealthCheck`用トリガーだけを削除する
- `テスト用の異常通知`: 本番URLを変更せず、予約済み`.invalid`ドメインの`https://fieldops-monitor-test.invalid`で異常経路を1回確認する
- `テスト状態を戻す`: 本番URLを確認し、復旧経路を1回確認する

削除対象はこのGASプロジェクト内で、ハンドラー名が`runHealthCheck`のトリガーだけに限定する。他のGASプロジェクトやトリガーには触れない。

## 9. 権限と安全性

必要な権限は次に限定する。

- 外部URLへのHTTPアクセス
- 現在のスプレッドシートの読み書き
- メール送信
- このスクリプトのトリガー管理

公開URLに認証情報を付与しない。GAS、スプレッドシート、GitHubへGoogleパスワード、Renderトークン、Cookie、APIキーを保存しない。

GASのトリガーは作成者のGoogleアカウント権限で動く。スプレッドシートの共有設定は非公開を維持する。

## 10. 障害時の動作

- スプレッドシートへの記録に失敗した場合も、状態変化があればメール通知を試行する。
- メール送信に失敗した場合はApps Script実行履歴で確認できるよう例外を再送出する。
- Script Propertiesが消えた場合は次回実行を初回として扱う。
- 同時実行は`LockService`で排他し、先行処理が残っている場合は後発実行を中止する。
- 設定値が空または不正な場合は外部アクセスせず、設定エラーを表示する。
- 同じ状態が続く限り、メールを繰り返し送らない。

## 12. テストと検証

### 12.1 リポジトリ内検証

- GASソースとマニフェストの必須ファイル確認
- 監視URLがHTTPSであること
- 時間トリガーが`everyHours(1)`であること
- 15分未満の定期トリガーが存在しないこと
- `/health/live`と`/health/ready`の両方を確認すること
- `muteHttpExceptions`を使用し、HTTP異常を記録できること
- 通知が状態変化時だけであること
- READMEに開始、停止、権限、復旧手順があること

### 12.2 GAS実環境検証

1. `初期設定を作成`を実行する。
2. 正常URLで`今すぐ確認`を実行し、履歴に正常が1行追加されることを確認する。
3. `テスト用の異常通知`を実行し、異常行と異常メールを確認する。
4. `テスト状態を戻す`を実行し、正常行と復旧メールを確認する。
5. `1時間ごとの監視を開始`を実行し、対象トリガーが1件であることを確認する。
6. 公開URL、通知先、権限、共有設定に秘密情報や意図しない公開がないことを確認する。

## 13. 導入手順

1. リポジトリでGASコード、検証スクリプト、運用手順を実装する。
2. ローカルテストとコードレビューを通す。
3. Googleスプレッドシート`FieldOps 公開監視`を作成する。
4. 紐づくApps Scriptへ検証済みソースとマニフェストを設定する。
5. Googleの権限確認画面で必要権限だけを承認する。
6. 正常・異常・復旧を実測する。
7. 1時間トリガーを登録する。
8. 実行後の監視履歴とメールを確認する。
9. GitHubへコミット・プッシュし、CI成功を確認する。

## 14. 停止と復旧

監視停止はスプレッドシートの`FieldOps監視`メニューから行い、`runHealthCheck`トリガーだけを削除する。コード、スプレッドシート、FieldOps本体は削除しないため、`1時間ごとの監視を開始`で再開できる。

GASが利用できない場合でも、FieldOps公開環境には影響しない。手動確認は`/health/live`と`/health/ready`へアクセスして行う。

## 15. 依存関係と制約

- GoogleアカウントでスプレッドシートとApps Scriptを作成できること
- 初回実行時に外部アクセス、メール、トリガーの権限承認が必要なこと
- Apps ScriptとメールにはGoogleの利用上限があり、上限は将来変更され得ること
- Render Freeのコールドスタートにより、監視1回の完了まで約1分以上かかる場合があること
- 1時間監視は1日24回であり、スリープを防止しないこと

## 16. 設計判断

1. **毎時監視を採用する。** 30分監視よりアクセス回数を抑え、15分未満のスリープ回避にならない。
2. **2つの既存ヘルスチェックを使う。** processとDB readinessを分けて診断できる。
3. **HTTP 200だけで正常にしない。** Renderの起動画面を正常と誤認しないため、本文`Healthy`も確認する。
4. **状態変化時だけ通知する。** 障害継続中のメール過多を避ける。
5. **スプレッドシートを操作面にする。** 非エンジニアでも履歴、設定、開始、停止を確認できる。
6. **FieldOps本体を変更しない。** 監視の追加・停止を公開アプリから分離し、可逆性を保つ。
